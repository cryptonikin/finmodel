### Как устроен `check` (4 запроса к API)
Для «Расчет инвестиций»: (1) список листов с `gridProperties`; (2) один `batchGet` строк заголовков всех листов
контракта (лист настроек читается целиком, он маленький); (3) один `batchGet` ключевых колонок — для последней
строки данных. Для «Бюджет и инвестиции - ai»: (4) только список листов (в контракте там лист без шапки).
Ретраи внутри клиента (429/5xx/сеть, пауза 2 → 4 с) в этот счёт не входят.

### Отклонения от ТЗ и почему
1. **Не хватало документов** — см. раздел 0. `DECISIONS_v1.5.md` не переименован в v1.6: менять файлы было запрещено.
2. §2 называет файл `docs/tasks/TASK_F0_v1.3.md`, а фактически ТЗ версии 1.4 — сохранено как `TASK_F0_v1.4.md`
   (правило DECISIONS №57: версия в имени файла).
3. **Python в контейнере Claude Code — 3.11.2** (3.12 нет, `ensurepip` отсутствует: venv создан через `get-pip.py`).
   Тесты прогнаны на 3.11; образ Docker — 3.12.16. Код совместим с ≥ 3.11 (`target-version = py311`).
4. Вместо `google-api-python-client` — REST Sheets API v4 через `google-auth` (`AuthorizedSession`) + `requests`:
   меньше зависимостей, scope задаётся явно, таймауты и ретраи под нашим контролем.
5. Добавлены файлы сверх §2: `app/context.py` (общий контекст), `app/jobs/cleanup.py`, `config/retention.yaml`,
   `config/settings_defaults.yaml`, `scripts/docker-cleanup.ps1` (всё это из §10/§13), `.gitattributes`
   (LF, а для `.ps1` — CRLF), `certs/README.md`.
6. `job_runs.status`: кроме `ok|warn|error` есть `running` (запуск идёт). `check` с кодом 1 (пропуски в таблице)
   записывается как `warn`, а не `error`: задача отработала, а планировщик не должен перезапускать её каждые 30 минут.
   Код **3** — «занято другой задачей» (файловая блокировка).
7. После ошибки задача повторяется не раньше чем через 30 минут (иначе планировщик запускал бы её каждую минуту).
8. Время задач из листа настроек (`schedule.<задача>`) планировщик берёт из **последнего успешного `check`**
   (сохраняется в SQLite `meta`), а не читает лист сам — без лишних запросов к API. В Ф0 ключ есть только для
   `tinvest_import`, а такой задачи пока нет: переопределение заработает в Ф1.
9. `docker compose config` не запускался (Docker в контейнере нет). Вместо этого `docker-compose.yml` разобран
   YAML-парсером с проверкой якорей: оба сервиса получают secrets, read_only, tmpfs 64m, cap_drop, logging и не имеют портов.
10. Для git в контейнере выполнено `git config --global --add safe.directory /workspace` (`/workspace` принадлежит root).

## 6. Риски и открытые вопросы

1. **Колонки с двумя писателями** («Акции», «Идеи», «Справочник») — в контракте только как документация; правило перед записью в эти листы — в Ф2 (раздел 9).
   Расхождения с §5 ТЗ не проверены. Первый реальный `check` покажет фактические пропуски и дубли.
2. **Заголовки по началу текста.** В «Акциях» есть «Цена» и «Цена к SMA200»: точное совпадение побеждает, это
   правильно. Но если в каком-то листе заголовок из контракта окажется началом двух других (например, «Статус»
   в «Кандидатах»), `check` честно выдаст неоднозначность — тогда нужно уточнить имя или указать `occurrence`.
3. ~~**Бэкапы «последние 10 и не старше 30 дней»** выполнены буквально~~ — **решено, см. раздел 8**: если записей в «Журнал» не будет больше
   30 дней, удалятся все бэкапы. Предложение: всегда оставлять хотя бы последний. Нужно решение.
4. **Сроки хранения:** DECISIONS №52 (60 дней логов / 365 дней `job_runs`) противоречит TASK_F0 v1.4 и DECISIONS №59
   (30 / 90). Взято 30 / 90 как более позднее решение.
5. ~~**Файловая блокировка**~~ — **решено порядком работы (раздел 8)**. **Файловая блокировка** (`flock` на `/data/finmodel.lock`) на bind-mount Windows (Docker Desktop/WSL2) может не
   работать между двумя контейнерами (`run --rm app` и `scheduler`). Внутри одного контейнера работает. Риск
   невелик: задачи только читают. Для записи в Ф1 нужна доп. защита (лист-флаг из §11.2).
6. ~~**Ротация лога в полночь**~~ — **решено, см. раздел 8**. **Ротация лога в полночь** идёт по системному времени контейнера. В slim-образе может не быть системной tzdata,
   тогда ротация будет в 03:00 МСК (00:00 UTC). Время в строках лога в любом случае МСК (pip-пакет `tzdata`).
7. **`cleanup` для таблиц Ф1** рассчитан на колонки `tinvest_operations.date_msk` (из TASK_F1 §3) и
   `tinvest_instruments.last_used_at` (в TASK_F1 не названа — нужно завести в Ф1). Пока таблиц нет, `cleanup` их пропускает.
8. **Окно операций** в `cleanup` = `period_months × 31 + 14` дней (с запасом). `period_months` берётся из последнего
   успешного `check` (лист настроек), по умолчанию 3.
9. **Первый старт планировщика** на пустой БД сразу выполнит `check` и `cleanup` как догон (последних запусков нет) —
   это ожидаемое поведение.
10. Dockerfile ещё не собирался (в контейнере Claude Code нет Docker) — проверить при первом `docker compose build`.
